# ADR-0005: AI の作りを見せて、人が承認する

- 状態: **案**(2026-10-31)。運営者が task 416 の PR で採るかを決める。設計は [docs/design/ai-architecture-review.md](../design/ai-architecture-review.md)
- 出典のタスク: jyoka/tasks#416
- 確認日: 2026-10-31。実モデルは呼んでいない
- 実装: task 422(2026-11-08)で、審査の画面、AI 構成書、指紋、関門 GA を作った。この ADR と違う所は [設計の 14 節](../design/ai-architecture-review.md#14-422-で決めたこと)(審査が要る試作品は「この設計で作る」を押した試作品にした、など)
- [ADR-0001](0001-local-runtime-and-isolation.md) の 3 つの層は弱めない。試作品から外への通信を足さない。[ADR-0003](0003-agent-simulation.md) の R2(`composition.json` のない試作品と今の構成は、変えずに動く)は守る

## 背景

- 今の設計は、構成の模擬を手段として「主役にしない」とした。構成は日常の言葉で選ばせ、Studio が裏で `app/composition.json` を書く形だった
- 運営者は 2026-10-31 に、これでは普通のプロダクトの試作と差がないと指摘した
- Studio がほかの道具と違うのは、AI の作りを動かして測れること。隠すと、この違いが消える

## 決定(案)

| 決めたこと | 中身 |
|---|---|
| 中心を変える | Studio の中心を「AI の作りを見せて、人が理解して承認する」にする。[vision.md](../vision.md) の原則 11 |
| 審査を置く | 作る前に、エージェントの構成、harness、データと RAG、技術の組の 4 つを審査する。承認がそろうまで作る AI を起動しない |
| 判断の順 | 固定の流れ、単一エージェント、マスターとサブの順に問い、足りたら止まる。「要らない」と言える |
| AI 同士の引き継ぎ | 選択肢にしない。人に渡すのは harness の条件にする。今の `handoffs` はデータとして残す |
| 「理想の構成」と言わない | 出すのは今日の一番良い推測。日付と根拠の場面を付ける。新しいモデルや作り方が出たら、同じ場面で測り直す。一番長く残る資産は場面の一覧 |
| 選択肢はデータ | 構成の選択肢、問いの文、本番の候補は Studio が持つデータにする。参加者の種類、ツールの処理、確かめの種類、守りの層はコードのまま |
| AI 構成書 | 結果を `.studio/reviews/<審査の ID>/architecture.json` に残す。承認した人、時刻、指紋を持つ |
| 審査が要る試作品 | これから新しく作る試作品だけ。飛ばすと「審査なし」の印が残る。今の試作品と見本は変えない |
| 関門 GA | G1 の直後、G2〜G4 の前に足す。承認した指紋と今の `app/` が違えば、試す欄を替える前に止め、審査に戻す。直すラウンドに回さない |
| 言葉 | AI の作りの言葉は隠さず、平たい言葉と並べる。開発の作業の言葉(`DEV_WORDS`)と、お客さんに見せる画面の決まりは変えない |
| 承認する人 | 会の中では、構成と技術の組は進行役、harness とデータと RAG は進行役と決める人の 2 人。1 人で使うときは本人 |

## ADR-0001 との関係

弱める決まりはありません。

| ADR-0001 の決まり | この ADR での扱い |
|---|---|
| 作る AI は `app/` だけを書く。`.studio/` はツールだけが書く | AI 構成書を `.studio/` に置く。この決まりを承認の守りに使う |
| 生成コードをサーバーで実行しない | 選択肢、案、AI 構成書は JSON のデータで、実行しない。式と関数は書かせない。案から `app/` に書くファイルの名前は Studio が決め、案にパスの欄を持たせない |
| 試作品の外への通信を許さない(`sandbox` の iframe と CSP) | 変えない。文書の検索(#421)は手元で動かす。案の数は `.studio/evals/` の結果から入れる |
| 127.0.0.1 とトークン | 変えない。審査の画面は今の Studio の画面に足す。1 台の PC の形(ADR-0004 の段 1)のまま |

案を出す AI は、聞き出しの AI(#382)と同じ決め方で起動します。ファイルを書かせず、返した JSON を Studio が検査します。Studio はその値を決まった名前のファイルに写します。

## ADR-0003 との関係

ADR-0003 は構成を測る土台で、この ADR はその上に人の承認を足します。

| ADR-0003 の決まり | この ADR での扱い |
|---|---|
| 構成をデータにする。構成 B は今のまま | 変えない。AI 構成書のない試作品で、関門 GA は「審査なし」で通す |
| 流用を受け入れ条件にする(R1〜R5) | 条件は変えない。「選択肢はデータ」は、R3 を審査の選択肢にも広げたもの。#419、#420、#421 は新しい処理を足すので R3 の例外で、理由を設計の 5 節に書いた。R2 の例外は、節を足すので直す `test/unit/blueprint.test.js` だけ |
| 構成 C(AI 同士の引き継ぎ) | データと動きは残す。案を出す AI は AI から AI への辺を出さない。お勧めの形ではないと読む |
| S10「プロダクト内 AI には道具を渡さない」(構成 B は今のまま) | 固定の流れでも、モデルにはツールを渡さない。呼ぶのはコード(#419)。モデルはツールを選ばないので、S10 と食い違わない。単一エージェント、マスターとサブでは、ADR-0003 のとおり構成に書いたツールだけを渡す |
| S16「何を聞くかはコードが決める」 | 固定の流れでは今のまま。単一エージェント、マスターとサブでは ADR-0003 のとおりモデルが決める。「モデル頼み」と画面に出す |
| 親子の委任がない | #420 で足した。データの形は agent-simulation.md の 2.9 |
| ツールの処理は 5 種類 | 文書の検索を足す(#421)。コードが要る所。手元で動かす |
| 関門の並び | G1 の直後に GA を足す。G2〜G4 は通ると試す欄を替えるので、その前に止める。コードだけで決まり、安い(S11) |
| 実モデルの回しは関門に入れない | 変えない。審査で実モデルを回すのは、人が頼み、同意と費用の上限を通したときだけ |
| 守りが減ったときの知らせ | 残す。GA で止めたときの違いの文に使う |

## 守りが崩れない理由

| 危険 | 守り |
|---|---|
| 作る AI が AI 構成書を書き換える | `.studio/` は作業の場所の外。今の閉じ込めで書けない(ADR-0001 の層 1) |
| 作る AI が承認後に構成を変える | Studio が指紋を比べる。AI の報告を信じない(今の G1 と同じ考え) |
| 作る AI が場面を弱めて数を良くする | AI 構成書の場面の指紋と違えば、数を「古い」と出す。今の `evalsChanged` は直すラウンドの分だけで、これを補う |
| 目録の指し先を替えて、関門を素通りする | 目録の `composition`、`ai` の値を指紋に入れる |
| 新しい試作品で AI 構成書が読めない | 止める。審査なしとして通さない |
| 案を出す AI が数を作る | 数は場面の回しの結果から Studio が入れる。案の検査で数の欄を受け付けない |
| お客さんの話を同意なしに送る | 案を出す AI は会の始めの同意の後だけ呼ぶ(ADR-0004) |

## 検討した候補

| 候補 | 長所 | 短所 | 判断 |
|---|---|---|---|
| a. 審査を作る前に置き、指紋で守る(この ADR) | 承認が残る。作り直しの前に止まる | 会の時間を使う。構成を変えるたびに承認が要る | **案** |
| b. 今のまま日常の言葉で選び、裏で書く | 速い。迷いが少ない | 普通の試作の道具と差がない。作りが分からないまま本番に渡る | 採らない |
| c. 見せるだけで承認を求めない | 止まらない | 誰が決めたかが残らない。「人が決める」に合わない | 採らない |
| d. AI 構成書を `app/` に置く | 版と一緒に動く | 作る AI が書ける。承認の記録にならない | 採らない |
| e. 引き継ぎも選択肢に残す | 今の構成 C をそのまま使える | 選択肢が増え、責任の所在が読みにくい | 採らない。データとしては残す |
| f. 関門 GA を直すラウンドに回す | 止まらずに進む | 作る AI が書き戻し、人の望んだ変更まで消える | 採らない |

## 残る危険

- 審査が長いと会が止まる。分の割り当ては推測で、K6 で測る
- 人が読まずに承認を押すことは、コードでは止められない。#396 の人の確かめで見る
- 1 台の PC の形では、承認した人の名前は申告。本人は確かめない
- 案を出す AI が同じ形ばかり勧めるか。#422 で形の違う架空の題材 3 つを 1 回ずつ通し、勧めた構成は 2 種類だった([real-review](../evidence/real-review/README.md))。マスターとサブを勧める題材は確かめていない
- 想像図は、このカードの実行では読めなかった(閲覧の権限がなかった)
