# Prototype Studio PRD

この文書は、jyoka/tasks#269(AIプロトタイピングツールのPRDと計画)の本文を写したものです。PRD の本文は書いた時点のまま残し、その後に決めたことは最後の「PRD の後に決めたこと」に書きます。食い違うときは「PRD の後に決めたこと」が正です。

## 位置づけ

このIssueは、独立したAIプロダクト向けプロトタイピングツールの親PRD。実装先はprivateリポジトリ https://github.com/jyoka/agent-prototype-studio 。aicaは最初の題材・参考情報であり、実装先ではない。子タスクは後述する。

## 課題

社内企画担当など非エンジニアが、AIプロダクトのアイデアを具体的な画面、会話、状態、データ、AIの振る舞いにして試すには、エンジニアへの依存や実装・接続の手間が大きい。静的な画面やモックだけでは実際のAIが自由な入力にどう反応するかわからず、実モデルだけで試すと再現性、コスト、UI変更のしやすさに課題がある。既存のコーディングツールの利用者はいても、企画担当は通常APIキーを持っていない。

## 解決策・ビジョン

非エンジニアが自然言語でAIプロダクトの体験を作成し、動くものを操作し、モックと実モデルの両方で試し、改善し、本番開発へ引き継げる独立した汎用プロトタイピングツールを目指す。対象はLINEに限定しない。aica風の求人相談は最初の検証対象であり、求人・LINE・既存aicaとの連携は共通基盤の前提にしない。

最初は利用者自身のPC上で動かすことを想定。社内企画担当の多くはKiroを利用しており、本人が認証済みのKiroを最初のAI接続候補とする。利用者は普段、APIキーやターミナルを意識せずブラウザで操作する。Cursorは後の候補。技術的・契約上の成立は未検証であり、Kiroで全機能が実現できると決めつけない。

## 長期ゴール: Stripeの設計思想に準じた高度な汎用・標準化基盤

StripeのHarbor、Drydock、Minions、Kaiは単なる参考事例ではなく、長期的な設計思想と目指す能力の基準。aicaは最初の実証例であって、完成目標をaica向けの小さな試作ツールに限定しない。利用者はStripeと同じ方向性の高度な汎用・標準化ツールを求めている。ただしStripe内部の非公開実装を再現できる、または同等の規模・性能が保証されるとは主張しない。

長期的に追求する能力と設計原則:

- 生成だけでなく、実行、コンパイル・実行時診断、画面や会話の観察、操作、修正を繰り返す閉ループ。プロダクト内AIも実際に試す。
- 特定製品に依存しない、複数ファイルの成果物と実行・プレビューの明確な境界。HarborのDrydockのように、再利用可能なレンダリング・実行能力を目指す。特定技術の採用やStripeの内部実装は未決定。
- 専門化された作成・調査・検証・本番実装などの能力を、共通の成果物や明確なツール境界を介して接続する。必要な機能を相互利用できるようにするが、初期からマルチエージェント化やMCPを必須としない。
- モデルが判断すべきことと、必ず実行すべき検証・権限確認・状態遷移などの決定的処理を分離する。
- 共有・レビュー・版管理・引き渡しに耐える成果物を目指す。将来的にはレビュー対象バージョンや変更に対するコメントの文脈・不確実性も扱う。実装順序は未決定。
- 既存のモデル接続やツール、設計システム、開発環境を再利用できる拡張性と、可観測性、隔離、適切な権限を設計する。標準化する契約は実例と利用から導く。
- プロトタイプを本番品質と混同せず、設計意図・状態・制約・未実装箇所を本番実装へ引き継げるようにする。

段階的な検証はゴールの縮小ではない。まずaica題材とKiroで縦切りの体験を実証し、実際の摩擦と結果を使って再利用可能な境界を育てる。初回実証に含めない共有・高度な協働・複数の接続方式なども、長期的な候補として維持する。各能力の具体的な受け入れ基準と優先順位は今後策定する。

## 利用者と体験

1. 企画担当者として、作りたいプロダクトと検証したい体験を自然言語で説明し、実装知識なしに試作を始めたい。
2. 企画担当者として、動く画面、会話、状態、架空データを含むプロトタイプを作りたい。
3. 企画担当者として、試作品を実際のユーザーの立場で操作し、体験の問題を見つけたい。
4. 企画担当者として、言葉で修正を依頼し、画面とAIの振る舞いを改善したい。
5. 企画担当者として、プロトタイプを作るAIへの指示と、試作中のプロダクト内AIへの発話を混同せずに使いたい。
6. 企画担当者として、モックで再現可能なシナリオを試し、画面や操作を比較したい。
7. 企画担当者として、同じ体験を実モデルで自由に試し、現実の応答やばらつきを知りたい。
8. 企画担当者として、何が実際のモデルで、何が架空データ・仮の保存・未接続なのかを知りたい。
9. 企画担当者として、エラーを理解し、修正を依頼できる説明を得たい。
10. 企画担当者として、テストの会話・状態をリセットし、同じ初期条件からやり直したい。
11. 企画担当者として、良い版を保存し、後から開き、変更前に戻りたい。
12. 企画担当者として、費用やデータ送信を理解した上で実モデルを試したい。
13. 企画担当者として、通常はコードやAPIキーを扱わずに使いたい。
14. 開発担当者として、必要な場合にプロンプト、AIの入出力、ツール呼び出し、状態変化、エラーを確認し、問題を切り分けたい。
15. 開発担当者として、ソース、意図、状態、モック、決定事項・未決定事項を引き継ぎ、本番実装に活かしたい。
16. 組織の管理者として、利用者本人の認証と承認済み利用条件のもとでデータと実行環境を扱いたい。
17. プロダクト担当者として、求人に限らず調査、学習、業務支援などのAI体験にも同じ仕組みを使いたい。

## 確定した方針と暫定的な設計

- 確定: 独立した汎用ツール。aicaは第一の題材。LINEへの展開は必須ではない。
- 確定: 非エンジニアが最初から自分で使える。自然言語による作成と修正を中心にする。
- 確定: モックと実モデルの両方が必要。最初の検証でも両方を含める。
- 確定: プロダクト内AIはツール内で新規に設定する方向。既存aicaエージェントへの接続を初期前提にしない。
- 確定: 最初は利用者自身のPCと本人が認証済みのKiroを優先して調査する。企画側にKiro利用者が多い。Cursorは将来の候補。
- 区別: プロトタイプを作るAIと、プロトタイプ内でユーザーに応答するAIは異なる役割。両方を同一CLIで実現できるかは未検証。
- 暫定: 「作る」会話と「試す」画面を分離。詳細としてAIの設定、入出力、ツール、状態、エラーを閲覧できるようにする。
- 暫定: プロトタイプは画面、AI設定、初期データ、状態、操作、意図、制約、バージョンを持つ成果物として扱う。具体的な形式・DSLは未決定。
- 暫定: 実行先への境界を設け、Kiroに固定しない。ただし初期から複数接続を作らない。
- 安全性: 実行される生成コードとエージェントのファイル・ネットワーク・外部コマンドは脅威モデルに基づき制限する。ブラウザ内実行だけで安全とみなさない。外部接続や公開は明示的に扱う。実データ・個人情報は初期検証に使わず、架空データを使う。

## 最初の検証題材

求職者が希望を話し、AIが理解した条件を表示し、本人が修正し、その修正を踏まえて会話を続ける。モックで一連の操作を確認し、実モデルでは自由な入力を試す。体験の作成、実行、観察、変更、再試行、保存を通して検証する。aicaにあるドメイン語を使う場合、「プロフィール」「雇用区分」「職種」「相談のまとめ」等はaicaの定義に合わせる。ただし汎用ツールの共通モデルを求人ドメインに固定しない。

## Kiroの先行調査・実証

公式情報と実際の利用条件を確認し、次の2用途を別々に検証する。

- 作るAI: 非対話実行、指示・出力、既存の本人認証、指定作業領域でのファイル編集、コマンド権限、エラー・中断。
- プロダクト内AI: 指示と会話履歴の引き継ぎ、構造化出力や必要なツール操作、応答速度、実行回数・同時実行・制限。
- 共通: 自動化と用途が契約・規約・社内ポリシーで許されるか、認証情報の保護、モデル送信内容、データ保持、利用費用、macOS / Windows、非エンジニア向け導入。
- 条件に合わなければ無理にCLIを使わない。作るAIとプロダクト内AIで接続先を分け、承認済みの代替手段を検討する。実際のAPI / モデル呼び出しには明示的許可と予算が必要。

## テスト方針・検証境界（提案、要確認）

実装詳細ではなく利用者から見える振る舞いを検証する。最高レベルでは、ブラウザから指示し、生成された試作を操作し、モックと実モデルを試し、変更・保存・再開する一連の体験を確認する。AI接続の境界では決定的な偽実装で認証・失敗・タイムアウト・会話履歴・状態変化を検証し、許可された範囲でKiroの実機スモークを別途行う。生成コードの実行・権限・データ分離を検証する。モックと実モデルの結果やテストした環境を区別して報告する。詳細な検証境界は実装計画を作る際に利用者と確認する。

## スコープ外・未決定

- 既存aicaへの組み込み、LINE / LIFF接続や実機保証は初期スコープ外。
- 本番品質の自動保証、生成物の自動デプロイ、実顧客データ接続は初期スコープ外。
- 複数人コメント、共有公開、複数CLIの初期実装は確定していない。利用状況に応じて後から検討。
- アプリ配布方式、実行・隔離の具体技術、標準化する成果物形式は未決定。
- プロンプト、モデル、AIの設定内容を利用者がどの深さまで直接編集するかは未決定。
- Kiroの機能・ライセンス・応答性能、社内承認は未確認。
