Prototype Studio

思いつきを AI プロダクトにすると、どんな作りになるか。動かして測り、人が承認してから作る。See how your idea works as an AI product, test it, and approve the architecture before you build.

AI プロダクトの作りは、エージェントの構成、harness(AI の周りで決まりを守らせるコード)、データと RAG、技術の組で決まります。An AI product's architecture comes down to four things: the agent setup, the harness (the code that keeps the AI within its rules), data and RAG, and the tech stack.

今は、目的の聞き出しから、設計の案内、AI 構成の審査(人が 4 つを承認する)、試して測る、人に見せる、引き継ぐまでが動きます。どれも、人の確かめ(初めての人や現場の会で使えるか)はまだです。まだできないことは作っているものに分けて書きました。Today it runs from the purpose interview through the design guide, the AI architecture review (a person approves four parts), trying and measuring, showing people, and handoff. None of it has been checked with people yet (whether first-time users or a live session can use it). What does not work yet is listed under In progress.

Studio が出すのは、日付と根拠のある、今日の一番良い推測です。本番の品質は約束しません。What Studio gives you is today's best guess, with a date and evidence. It does not promise production quality.

試すのはモックで、料金はかかりません。本物の AI は、画面で同意したときと、--real で場面を回すときだけ使います。Trying runs on a mock and costs nothing. The real model runs only when you consent on screen, or when you run evals with --real.

今できることWhat it does today

どれも今の Studio で動きます。人の確かめ(初めての人や現場の会で使えるか)は、まだです。絵は Studio が自分で撮った画面です。押すと、その機能の docs が開きます。All of this works in Studio today. None of it has been checked with people yet (whether first-time users or a live session can use it). The images are screens Studio took of itself. Click one to open the docs for that feature.

  • 誰 → 何の問題 → 場面 → 成功の印 → しないことwho → problem → scene → sign of success → out of scope

    目的の聞き出しPurpose interview

    思いつきを 1 文書くと、問いが 1 つずつ返り、目的の文書になる。Write your idea in one sentence. Studio asks one question at a time and turns the answers into a purpose document.

    決まるのは「これで決める」を押したときだけ。文書は .studio/intent.json に残る。Nothing is decided until you press the button. The document stays in .studio/intent.json.

  • 要点 → 要求、使う人、場面、決まりごと、データnotes → needs, users, scenes, rules, data

    ヒアリングの整理Hearing notes

    打った要点を AI が 5 つの欄に振り分け、決める人が確かめる。The AI sorts the notes you type into five columns, and the person who decides checks them.

    本物の AI は同意の後だけ動き、同意しないときは手で振り分ける。本物のお客さんの会には、まだ使わない。板は .studio/organize.json に残る。The real model runs only after you consent. Without consent, you sort the notes by hand. Do not use it in real customer sessions yet. The board stays in .studio/organize.json.

  • 問題 → 使う人 → 場面 → データ → 構成 → 画面problem → users → scenes → data → setup → screens

    設計の案内Design guide

    問題、使う人、場面、データ、構成、画面の 6 つの段で、2〜3 の案から選ぶ。Pick from two or three proposals at each of six steps: problem, users, scenes, data, setup, and screens.

    案は出した日付つきの今日の推測で、まだ測っていない。選んだ場面と構成と架空のデータを Studio が書き、設計は .studio/design.json に残る。Each proposal is today's guess, dated, and not measured yet. Studio writes the chosen scenes, setup, and sample data, and the design stays in .studio/design.json.

  • AI 構成の審査AI architecture review

    エージェントの構成、harness、データと RAG、技術の組の 4 つを読み、欄ごとに承認する。4 つそろうまで作る AI は動かない。Read the agent setup, harness, data and RAG, and tech stack, and approve each one. The maker AI waits until all four are approved.

    構成は固定の流れ、単一エージェント、マスターとサブから選び直せる。承認は AI 構成書(.studio/reviews/)に残り、承認の後に構成が変わると関門で止まる。You can switch between a fixed flow, a single agent, and a master with sub-agents. Approvals stay in the AI architecture record (.studio/reviews/), and a later change to the setup stops at a gate.

  • 表 → ツールで引く、決まり → プロンプト、長い文書 → RAG?table → tool, rule → prompt, long document → RAG?

    データの棚と RAG の判定Data shelf and RAG check

    AI が何をどう読むかを棚で見せ、RAG が要るかを判定する。「要らない」とも言う。A shelf shows what the AI reads and how, and checks whether RAG is needed. The answer can be no.

    最初の判定は今日の推測。RAG ありとなしを同じ場面の一覧で回すと、回した結果を根拠に判定し直す。The first check is today's guess. Run the same evals with and without RAG, and the check is redone from those results.

  • 構成の模擬Simulated setups

    構成と前提を選ぶと、同じ試作品が別の組み方で話す。模擬のエージェントがツールを自分で選んで呼ぶ。Pick a setup and assumptions, and the same prototype talks in a different arrangement. A simulated agent picks and calls the tools itself.

    構成はデータで、app/composition.json に書く。A setup is data, written in app/composition.json.

  • 守りの層Guardrail layers

    どの層の守りが止めたかと、その理由を実行の記録で読む。Read in the trace which guardrail layer stopped a turn, and why.

    層はツールの守り、プロンプトの頼み、出口の確かめの 3 つ。1 ターンの要約は試す欄の下、全部は「開発者向けの詳細」にある。The layers are tool guards, prompt asks, and output checks. A one-turn summary sits under the try pane, and the full trace is under developer details.

  • 場面の比較Eval runs

    同じ場面の一覧を構成と前提ごとに回し、1 つの表で比べる。Run the same evals across setups and assumptions, and compare them in one table.

    試す欄の下の表か、ターミナル(npm run evals)で回す。モックの数は形の確かめで、振る舞いの差は実モデルで測る。Run it from the table under the try pane or in the terminal (npm run evals). Mock numbers only check the shape. Differences in behavior need the real model.

  • 質の見直しQuality review

    アクセシビリティ、字と地の差、素材に合うか、場面の結果、費用を 1 つの表で見る。各行に「なぜ大事か」と「直す」が付く。See accessibility, text contrast, fit with the design materials, eval results, and cost in one table. Each row says why it matters and how to fix it.

    測ったものと AI の判断を分け、見ていない項目は「まだ見ていない」と出す。アクセシビリティは Studio の小さな検査だけ。Measured items are kept apart from AI judgments, and unchecked items say so. Accessibility uses only a small check built into Studio.

  • 言葉で直す欄Plain-word edits

    試しながら、画面や AI の振る舞いの直したい所を言葉で頼む。While you try the prototype, ask in plain words for changes to the screens or the AI's behavior.

    作る AI が書けるのは、試作品の app/ だけ。The maker AI can write only to the prototype's app/.

  • 試作品 + 確かめたい問い → 答えを版に残すprototype + questions → answers kept with the version

    人に見せるShowing people

    試作品と確かめたい問いだけの画面にして、相手に触ってもらう。開発の欄は隠れる。Switch to a screen with only the prototype and the questions to check, and let people try it. The developer panels are hidden.

    問いは目的の文書の成功の印から作り、答えは見せた版に残る。手元の PC で見せる形だけで、公開はしない。The questions come from the success signs in the purpose document, and the answers stay with the version you showed. It works only on your own PC, with no public sharing.

  • コメント → 承認 → 作る AI が直す → 前と後comment → approve → maker AI fixes → before and after

    みんなで作るBuilding together

    見せる画面の場所にコメントを付け、承認したコメントだけを作る AI が直す。反応をいくつ付けても動かない。Comment on a place in the showing screen. The maker AI acts only on approved comments, no matter how many reactions there are.

    1 台の PC でみんなで使う形。直した記録、前と後の比べ、元に戻すがある。構成のコメントは審査に戻す。A group shares one PC. It keeps a fix record, a before-and-after view, and undo. Architecture comments go back to the review.

  • app/ → 版version → handoffs/

    版と引き継ぎVersions and handoff

    良い状態を版として保存し、いつでも戻す。本番開発に渡すものを 1 つのフォルダーに書き出す。Save a good state as a version and restore it any time. Export what the production team needs to one folder.

    ソース、AI の設定、試した会話、証拠の要約が入る。It holds the source, AI settings, tried conversations, and an evidence summary.

  • 検査 → ビルド → 場面 → 起動 → シナリオchecks → build → evals → launch → scenarios

    作るループの関門Build-loop gates

    作る AI が直すたびに、Studio が決まった順に確かめる。落ちたら失敗を返し、2 回まで直させる。After each edit by the maker AI, Studio runs its checks in a fixed order. On failure, it sends the result back for up to two fix rounds.

    順は検査、ビルド、場面、起動、シナリオ。The order is checks, build, evals, launch, and scenarios.

3 つの問いThree questions

Studio が何をするかを、3 つの問いに答えて書きます。今できることと、作っているものを分けます。What Studio does, answered as three questions. What works today is kept apart from what is in progress.

問いQuestion Prototype Studio
AI の作りを見せるかDoes it show the AI architecture? 見せる。設計の案内で構成の案を並べ、AI 構成の審査で構成、harness、データと RAG、技術の組を図と表で見せ、実行の記録で構成、プロンプトの部品、ツール、守りの判定を見せる。人の確かめはまだ。Yes. The design guide lists setup proposals, the AI architecture review shows the setup, harness, data and RAG, and tech stack in diagrams and tables, and the trace shows the setup, prompt parts, tools, and guardrail verdicts. It has not been checked with people yet.
人が承認するかDoes a person approve it? 承認する。設計の案内の後の AI 構成の審査で、4 つを承認するまで作る AI を起動しない。承認の後に構成が変わると、関門で止まる。人の確かめはまだ。ほかに、目的の文書と設計の案を人が押して決める段、コメントを承認してから直す流れ、本物の AI を使う前の同意がある。Yes. 測るかDoes it measure? 測る。場面を構成と前提ごとに回し、1 つの表で比べる(試す欄の下か npm run evals)。質の見直しで、アクセシビリティ、字と地の差、費用も並べる。モックの数は形の確かめだけで、案の良し悪しの根拠にしない。Yes. Mock numbers only check the shape, and are not evidence for choosing a proposal.
